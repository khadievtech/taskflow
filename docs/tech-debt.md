# Technical Debt Register

Сводный список известных пробелов в проекте. Каждый пункт — осознанное,
явно принятое решение "не делать X сейчас", а не забытая проблема.

Формат: что не сделано → почему это приемлемо сейчас → что стриггерит фикс →
ссылка на GitHub Issue для трекинга.

Правило: любой новый осознанный пробел фиксируется здесь **в том же PR**,
где он появился — так долг не накапливается незаметно.

---

## 1. Frontend использует mock-данные вместо реального API

**Где**: `frontend/src/api/tasks.ts` — `MOCK_TASKS` вместо `fetch('/api/v1/tasks')`.

**Почему приемлемо сейчас**: frontend-скелет собирался на Phase 0, когда
backend ещё не имел рабочего `/api/v1/tasks` (появился только на Phase 0.5).
Kanban-доска нужна была, чтобы визуально проверить design tokens и
CORS-связку, не дожидаясь backend.

**Триггер для фикса**: в любой момент — эндпоинт уже готов и протестирован
через curl. Чисто вопрос приоритета, не блокер.

**Issue**: #1 (создать вручную, см. инструкцию ниже)

## 2. Тесты backend делят БД с локальной разработкой

**Где**: `backend/tests/conftest.py` — `DATABASE_URL` берётся из того же
`.env`, что и `uvicorn --reload` при ручной разработке.

**Почему приемлемо сейчас**: в CI (`.github/workflows/ci.yml`) это уже не
проблема — там поднимается чистый Postgres service-контейнер на каждый
запуск. Проблема остаётся только при локальном запуске тестов на
голом железе (не через Docker Compose).

**Связанная проблема (не отмечена изначально)**: тесты не изолируют состояние
друг от друга. В `pyproject.toml` стоит `asyncio_default_test_loop_scope =
"session"` (обходной путь для конфликта pytest-asyncio с async-engine
SQLAlchemy), и нет отката транзакции после каждого теста. В результате
`test_list_tasks` видит задачи, созданные другими тестами — сейчас проверки
написаны так, что это не ломает их (`assert "Task A" in titles`, а не
проверка точного количества), но это хрупко: любой тест, проверяющий число
записей, начнёт падать в зависимости от порядка выполнения.

**Триггер для фикса**: Phase 1 (Docker Compose) уже частично решает это —
можно поднять отдельный сервис `postgres-test` в `docker-compose.yml` для
локальных тестов. Полное решение — фикстура, оборачивающая каждый тест в
транзакцию с rollback вместо commit.

**Issue**: #2

## 3. Frontend-компоненты не покрыты тестами

**Где**: `frontend/src/components/StatusPanel.tsx`, `TaskBoard.tsx` — нет
`*.test.tsx` файлов вообще.

**Почему приемлемо сейчас**: 2 небольших презентационных компонента,
логика тривиальна (рендер + один `fetch` в `useEffect`). Риск регрессии
низкий при таком масштабе.

**Триггер для фикса**: когда появится первая форма с валидацией или
логика ветвления в компоненте (например, создание задачи с обязательными
полями) — добавить `vitest` + `@testing-library/react`.

**Issue**: #3

## 4. Нет End-to-End тестов

**Где**: отсутствуют полностью — нет `playwright`/`cypress` в проекте.

**Почему приемлемо сейчас**: E2E — самый дорогой в поддержке вид тестов
(медленные, флаки на CI, требуют поднятого полного стека). Для
одностраничного pet-проекта на раннем этапе ROI низкий.

**Триггер для фикса**: когда появится первый реальный критичный
пользовательский сценарий (например, "создать задачу → назначить →
перевести в Done"), который дорого сломать незаметно — тогда 1-2 E2E-теста
на самый важный путь, не более.

**Issue**: #4

## 5. Prod-стек работает без аутентификации

**Где**: все эндпоинты `/api/v1/tasks` открыты — нет ни авторизации, ни
rate limiting.

**Почему приемлемо сейчас**: стек доступен только внутри домашней локальной
сети (нет проброса портов на роутере, нет публичного IP). Поверхность
ограничена устройствами в вашем Wi-Fi.

**Почему это всё же долг, а не просто «Phase 6 по плану»**: приложение уже
**развёрнуто и работает**, то есть экспозиция реальная, а не гипотетическая.
Любое устройство в сети может создавать и удалять задачи.

**Триггер для фикса**: обязательно **до** того, как стек станет доступен за
пределами локальной сети (проброс порта, VPS, публичный домен). Реализация —
Phase 6.

**Issue**: создать вручную

## 6. Миграции выполняются в entrypoint каждой реплики

**Где**: `backend/docker-entrypoint.sh` — `alembic upgrade head` перед стартом
приложения.

**Почему приемлемо сейчас**: одна реплика backend, конфликта нет. Alembic
дополнительно использует advisory lock в Postgres.

**Почему это блокер для Phase 7**: при нескольких репликах в Kubernetes
каждый под попытается применить миграции одновременно. Правильная практика —
вынести миграции в отдельный `Job` или init-container, выполняемый один раз
перед раскаткой новых реплик.

**Триггер для фикса**: Phase 7 (Kubernetes), до увеличения числа реплик
больше одной.

**Issue**: создать вручную

## 7. `VITE_API_URL` запекается в бандл на этапе сборки

**Где**: `frontend/Dockerfile` (build-arg) + `frontend/src/api/client.ts`.

**В чём проблема**: Vite встраивает значение прямо в JS-бандл. Поменять адрес
backend после сборки нельзя — только пересобрать образ. Плюс адрес сейчас
привязан к IP, который роутер выдаёт по DHCP: после его смены приложение
перестанет находить backend, и потребуется новая сборка образа.

**Почему приемлемо сейчас**: адрес меняется редко, пересборка через CD
занимает минуты и делается автоматически.

**Триггер для фикса**: при появлении домена/HTTPS (Phase 5) или нескольких
окружений (staging/prod) из одного образа. Решение — runtime-конфиг:
nginx через `envsubst` генерирует `config.js` при старте контейнера, либо
frontend забирает конфиг с эндпоинта backend. Тогда один образ работает в
любом окружении — это и есть 12-factor подход.

Как немедленная страховка: зарезервировать текущий IP за MAC-адресом в
настройках роутера (DHCP reservation).

**Issue**: создать вручную

## 8. Сервисы обновляются вразнобой (version skew)

**Где**: следствие pull-модели — см. `docs/adr/0002-pull-based-deployment.md`.

**В чём проблема**: наблюдалось расхождение ~2.5 минуты между обновлением
frontend и backend (arm64-сборка backend под QEMU идёт дольше, и Watchtower
нашёл новый образ позже). В этот промежуток новый frontend работал со старым
backend.

**Почему приемлемо сейчас**: API пока не менялся ломающим образом, и
пользователь один.

**Триггер для фикса**: перед первым breaking change в API. Варианты —
поддерживать обратную совместимость API на время раскатки (стандартная
практика), либо перейти на управляемую стратегию rolling update в
Kubernetes (Phase 7).

**Issue**: создать вручную

## 9. Слой зависимостей backend не кэшируется отдельно

**Где**: `backend/Dockerfile`, стадии `dev` и `builder` — `COPY . .` идёт
перед `pip install`.

**В чём проблема**: любое изменение в `app/` инвалидирует слой установки
зависимостей, и pip переустанавливает всё заново при каждой сборке. Это
удлиняет CD.

**Почему приемлемо сейчас**: зависимостей немного, сборка укладывается в
приемлемое время.

**Триггер для фикса**: когда время сборки начнёт мешать. Решение — вынести
зависимости в отдельный файл (`requirements.txt` / `uv.lock`) и копировать
его отдельным слоем **до** копирования кода.

**Issue**: создать вручную

## 10. Multi-arch сборка идёт через эмуляцию QEMU

**Где**: `.github/workflows/cd.yml` — `platforms: linux/amd64,linux/arm64`
на amd64-раннере.

**В чём проблема**: arm64-вариант собирается под эмуляцией — минуты вместо
секунд.

**Почему приемлемо сейчас**: коммиты редкие, минуты CI не критичны.

**Триггер для фикса**: если время CD станет мешать. Решение — собирать каждую
архитектуру на нативном раннере (`ubuntu-24.04-arm` доступен бесплатно для
публичных репозиториев) и сшивать multi-arch манифест отдельным шагом.

**Issue**: создать вручную

## 11. Секреты хранятся открытым текстом в `.env` файлах

**Где**: `.env`, `.env.prod` на диске; пароль Postgres в открытом виде.

**Почему приемлемо сейчас**: файлы не в git (проверено `git check-ignore`),
пароль от локальной БД в изолированной Docker-сети, доступной только внутри
хоста.

**Триггер для фикса**: перед выходом за пределы локальной сети или появлением
реально чувствительных секретов (API-ключи платёжек, токены). Решения по
возрастанию сложности — Docker secrets, SOPS/age с шифрованием в git,
Kubernetes Secrets + External Secrets Operator (Phase 7-8), HashiCorp Vault.

**Issue**: создать вручную
