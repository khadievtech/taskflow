Сводный список известных пробелов в проекте. Каждый пункт — осознанное,
явно принятое решение "не делать X сейчас", а не забытая проблема.

Формат: что не сделано → почему это приемлемо сейчас → что стриггерит фикс →

где он появился — так долг не накапливается незаметно.

## 1. ~~Frontend использует mock-данные вместо реального API~~ — ЗАКРЫТО (Phase 5a)

**Как закрыто**: `MOCK_TASKS` удалён. Появились клиент API
(`src/api/tasks.ts` — list/create/update/delete с разбором ошибок FastAPI),
хук состояния (`src/hooks/useTasks.ts`), форма создания задачи и карточка с

<details><summary>Исходное описание проблемы</summary>

**Почему приемлемо сейчас**: frontend-скелет собирался на Phase 0, когда
backend ещё не имел рабочего `/api/v1/tasks` (появился только на Phase 0.5).
Kanban-доска нужна была, чтобы визуально проверить design tokens и
CORS-связку, не дожидаясь backend.

**Триггер для фикса**: в любой момент — эндпоинт уже готов и протестирован
через curl. Чисто вопрос приоритета, не блокер.

</details>

## 2. Тесты backend делят БД с локальной разработкой

**Где**: `backend/tests/conftest.py` — `DATABASE_URL` берётся из того же
`.env`, что и `uvicorn --reload` при ручной разработке.

**Почему приемлемо сейчас**: в CI (`.github/workflows/ci.yml`) это уже не
проблема — там поднимается чистый Postgres service-контейнер на каждый
запуск. Проблема остаётся только при локальном запуске тестов на
голом железе (не через Docker Compose).

**Связанная проблема (не отмечена изначально)**: тесты не изолируют состояние
друг от друга. В `pyproject.toml` стоит `asyncio_default_test_loop_scope =
"session"` (обходной путь для конфликта pytest-asyncio с async-engine
SQLAlchemy), и нет отката транзакции после каждого теста. В результате
`test_list_tasks` видит задачи, созданные другими тестами — сейчас проверки
написаны так, что это не ломает их (`assert "Task A" in titles`, а не
проверка точного количества), но это хрупко: любой тест, проверяющий число
записей, начнёт падать в зависимости от порядка выполнения.

**Триггер для фикса**: Phase 1 (Docker Compose) уже частично решает это —
можно поднять отдельный сервис `postgres-test` в `docker-compose.yml` для
локальных тестов. Полное решение — фикстура, оборачивающая каждый тест в
транзакцию с rollback вместо commit.

**Issue**: #2

мокирования fetch, и их поведение проверяется сквозными проверками.

<details><summary>Исходное описание проблемы</summary>

**Где**: `frontend/src/components/StatusPanel.tsx`, `TaskBoard.tsx` — нет
`*.test.tsx` файлов вообще.

**Почему приемлемо сейчас**: 2 небольших презентационных компонента,
логика тривиальна (рендер + один `fetch` в `useEffect`). Риск регрессии
низкий при таком масштабе.

**Триггер для фикса**: когда появится первая форма с валидацией или
логика ветвления в компоненте (например, создание задачи с обязательными
полями) — добавить `vitest` + `@testing-library/react`.

## 5. ~~Prod-стек работает без аутентификации~~ — ЗАКРЫТО (Phase 6a)

**Как закрыто**: все эндпоинты задач требуют аутентификации — зависимость
объявлена на уровне роутера, поэтому новый эндпоинт нельзя случайно оставить
открытым. Health-check намеренно остался публичным: его опрашивают Docker и
Kubernetes, у которых нет учётных данных.

Реализация: пользователи в таблице `users`, пароли через Argon2id (pwdlib),
токен JWT (PyJWT) в httpOnly cookie с SameSite=Lax. Регистрацию можно закрыть
переменной `ALLOW_REGISTRATION=false` после создания своей учётной записи.
Приложение отказывается стартовать в production с ключом подписи по умолчанию.

Что НЕ закрыто и вынесено отдельными пунктами: rate limiting на вход (19),
отсутствие подтверждения email и восстановления пароля (20), задачи не
привязаны к владельцу (21).

<details><summary>Исходное описание проблемы</summary>

**Где**: все эндпоинты `/api/v1/tasks` открыты — нет ни авторизации, ни
rate limiting.

**Почему приемлемо сейчас**: стек доступен только внутри домашней локальной
сети (нет проброса портов на роутере, нет публичного IP). Поверхность
ограничена устройствами в вашем Wi-Fi.

**Почему это всё же долг, а не просто «Phase 6 по плану»**: приложение уже
**развёрнуто и работает**, то есть экспозиция реальная, а не гипотетическая.
Любое устройство в сети может создавать и удалять задачи.

**Триггер для фикса**: обязательно **до** того, как стек станет доступен за
пределами локальной сети (проброс порта, VPS, публичный домен). Реализация —
Phase 6.

</details>

## 6. Миграции выполняются в entrypoint каждой реплики

**Где**: `backend/docker-entrypoint.sh` — `alembic upgrade head` перед стартом
приложения.

**Почему приемлемо сейчас**: одна реплика backend, конфликта нет. Alembic
дополнительно использует advisory lock в Postgres.

вынести миграции в отдельный `Job` или init-container, выполняемый один раз
перед раскаткой новых реплик.

**Триггер для фикса**: Phase 7 (Kubernetes), до увеличения числа реплик
больше одной.

## 7. ~~`VITE_API_URL` запекается в бандл на этапе сборки~~ — ЗАКРЫТО (Phase 5a)

**Как закрыто**: фронтенд переведён на относительные пути (`/api/v1/...`),
которые маршрутизирует обратный прокси. Адрес backend в бандл больше не
попадает — проверено поиском по собранному файлу. Значение `ARG VITE_API_URL`
по умолчанию пусто, build-arg из `cd.yml` убран, repository variable
`PROD_API_URL` больше не используется. В dev-режиме ту же роль играет
`server.proxy` в `vite.config.ts`, поэтому dev и prod ведут себя одинаково.

Побочный эффект: CORS перестал участвовать вообще — запросы идут на тот же
origin, что и страница.

<details><summary>Исходное описание проблемы</summary>

**Где**: `frontend/Dockerfile` (build-arg) + `frontend/src/api/client.ts`.

**В чём проблема**: Vite встраивает значение прямо в JS-бандл. Поменять адрес
backend после сборки нельзя — только пересобрать образ. Плюс адрес сейчас
привязан к IP, который роутер выдаёт по DHCP: после его смены приложение
перестанет находить backend, и потребуется новая сборка образа.

**Почему приемлемо сейчас**: адрес меняется редко, пересборка через CD
занимает минуты и делается автоматически.

**Триггер для фикса**: при появлении домена/HTTPS (Phase 5) или нескольких
окружений (staging/prod) из одного образа. Решение — runtime-конфиг:
nginx через `envsubst` генерирует `config.js` при старте контейнера, либо
frontend забирает конфиг с эндпоинта backend. Тогда один образ работает в
любом окружении — это и есть 12-factor подход.

Как немедленная страховка: зарезервировать текущий IP за MAC-адресом в
настройках роутера (DHCP reservation).

</details>

## 9. Слой зависимостей backend не кэшируется отдельно

**Где**: `backend/Dockerfile`, стадии `dev` и `builder` — `COPY . .` идёт
перед `pip install`.

**В чём проблема**: любое изменение в `app/` инвалидирует слой установки
зависимостей, и pip переустанавливает всё заново при каждой сборке. Это
удлиняет CD.

**Почему приемлемо сейчас**: зависимостей немного, сборка укладывается в
приемлемое время.

**Триггер для фикса**: когда время сборки начнёт мешать. Решение — вынести
зависимости в отдельный файл (`requirements.txt` / `uv.lock`) и копировать
его отдельным слоем **до** копирования кода.

**Issue**: создать вручную

## 12. ~~Эндпоинт `/metrics` открыт всем в локальной сети~~ — ЗАКРЫТО (Phase 5a)

**Как закрыто**: обратный прокси возвращает 404 на `/metrics` (точное
совпадение пути, наивысший приоритет в nginx). Порт backend привязан к
`127.0.0.1`, поэтому напрямую снаружи недоступен. Инструменты наблюдения
(Grafana, Prometheus, Alertmanager, Loki, Alloy) тоже привязаны к
`127.0.0.1` и больше не видны из локальной сети.

Мониторинг при этом работает: Prometheus скрейпит `backend:8000` напрямую
по внутренней docker-сети, минуя прокси.

<details><summary>Исходное описание проблемы</summary>

**Где**: `backend/app/main.py` — Instrumentator публикует `/metrics` на том же
порту 8000, который проброшен наружу в `docker-compose.prod.yml`.

**В чём проблема**: метрики раскрывают внутреннее устройство сервиса — полный
список эндпоинтов, частоту ошибок, латентности, версию Python. Для атакующего
это готовая карта поверхности. Grafana на порту 3000 в той же ситуации.

**Почему приемлемо сейчас**: доступ ограничен локальной сетью, порты наружу
не проброшены.

**Триггер для фикса**: обязательно до выхода за пределы локальной сети.
Решения — публиковать метрики на отдельном внутреннем порту, недоступном с
хоста; либо закрыть путь `/metrics` на уровне reverse proxy (Phase 5);
либо вынести в отдельную сеть, видимую только Prometheus.

</details>

## 13. Alloy читает сокет Docker от root

**Где**: `docker-compose.observability.yml`, сервис `alloy` — монтирует
`/var/run/docker.sock` и работает с `user: root`.

**В чём проблема**: доступ к сокету Docker равносилен правам root на хосте —
через него можно запустить контейнер с любыми привилегиями. Формально сокет
смонтирован `:ro`, но это ограничивает лишь запись в файл сокета, а не набор
доступных API-вызовов.

**Почему приемлемо сейчас**: root нужен потому, что образ Alloy работает от
UID 473, которому сокет недоступен. Домашняя машина, доверенный образ из
официального репозитория Grafana.

**Триггер для фикса**: при выносе на машину, где важна изоляция. Решения —
поставить между Alloy и сокетом `docker-socket-proxy`, разрешающий только
нужные эндпоинты (containers, logs); либо перейти на чтение файлов логов
напрямую вместо Docker API; либо в Kubernetes (Phase 7) использовать
чтение с файловой системы узла, где сокет не нужен вообще.

**Issue**: создать вручную

## 14. Нет метрик контейнеров (CPU, память, сеть, диск)

**Где**: `observability/prometheus/prometheus.yml` — цели только backend,
Prometheus и postgres-exporter.

**В чём проблема**: четвёртый золотой сигнал (saturation) покрыт лишь по
соединениям Postgres. Не видно, упирается ли контейнер в лимит памяти, растёт
ли потребление CPU, забивается ли диск.

**Почему приемлемо сейчас**: подробное обоснование в
`docs/adr/0003-defer-container-metrics.md`. Кратко: cAdvisor не работает на
Docker Desktop для Mac (текущая площадка) и сломан с Docker 29 на Linux
(будущая площадка). Добавлять непроверяемый компонент хуже, чем явно
зафиксировать пробел.

**Триггер для фикса**: наиболее вероятно — переход в Kubernetes (Phase 7),
где метрики контейнеров отдаёт kubelet через встроенный cAdvisor, и пробел
закрывается сам. Если понадобятся раньше — рабочий и проверяемый путь есть
(Docker Stats API через отдельный OTel Collector, Вариант D в ADR), но эта
работа была бы одноразовой: в Kubernetes источник метрик другой.

**Issue**: создать вручную

**Где**: `frontend/nginx.conf` — используется формат access-лога по умолчанию.

стадию `stage.json` в `observability/alloy/config.alloy` для этого сервиса.

## 17. Конфигурации мониторинга не доставляются на сервер автоматически

**Где**: `observability/` — правила алертов, конфиги Prometheus, Loki, Alloy,
Alertmanager и дашборды Grafana.

**В чём проблема**: код приложения доставляется автоматически (CD публикует
образ в GHCR, Watchtower подтягивает его на хосте). Конфигурации мониторинга
приезжают иначе — они смонтированы в контейнеры bind-mount'ом из рабочей
копии репозитория, а не вкомпилированы в образ. Значит на сервере нужно
вручную выполнить `git pull`, а затем перечитать конфиг:
`curl -X POST http://localhost:9090/-/reload`.

Практическое следствие: новое правило алерта, смёрженное в `main`, на сервере
не появится, пока кто-то не зайдёт туда руками. Об этом легко забыть, и
расхождение обнаружится в худший момент — когда алерт должен был сработать,
но его там не было.

**Почему приемлемо сейчас**: стек развёрнут на той же машине, где ведётся
разработка, поэтому рабочая копия всегда актуальна. Проблема проявится ровно
в тот момент, когда появится отдельный сервер.

**Триггер для фикса**: появление отдельного сервера. Варианты по возрастанию
зрелости:
- периодический `git pull` по cron или systemd timer на сервере;
- запечь конфиги в собственный образ поверх официального — тогда они поедут
  тем же путём, что и код, но потеряется возможность быстрой правки на месте;
- GitOps (Flux, ArgoCD) — инструмент следит за репозиторием и применяет
  изменения сам. Это естественный путь на Phase 7, где конфигурации живут
  в ConfigMap, а не файлами на диске.

## 18. Типы фронтенда синхронизируются с бэкендом вручную

**Где**: `frontend/src/api/tasks.ts` — интерфейсы `Task`, `TaskCreate`,
`TaskUpdate` повторяют схемы Pydantic из `backend/app/schemas/task.py`.

**В чём проблема**: при изменении схемы на бэкенде фронтенд об этом не узнает.
TypeScript будет уверен, что поле есть, а в ответе его не окажется — ошибка
всплывёт только в рантайме, у пользователя. Классический пример: переименовали
`assignee` в `assignee_id`, тесты фронтенда прошли (там свои фикстуры),
сборка прошла, а приложение сломалось.

**Почему приемлемо сейчас**: три интерфейса и одна сущность. Генератор типов
принёс бы больше движущихся частей, чем экономии.

**Триггер для фикса**: появление 3-4 сущностей, либо первое расхождение,
дошедшее до рантайма. Решение — генерация типов из OpenAPI-схемы, которую
FastAPI отдаёт автоматически: `openapi-typescript` или `orval`, шагом в CI.
Тогда расхождение схемы и клиента ловится на этапе сборки, а не в проде.

**Issue**: создать вручную

## 19. Нет ограничения частоты попыток входа

**Где**: `POST /api/v1/auth/login` — можно перебирать пароли без ограничений.

**В чём проблема**: Argon2id намеренно вычислительно дорог, что замедляет
перебор, но не исключает его. Хуже другое: каждая попытка тратит процессор
сервера, поэтому поток запросов на вход становится способом вызвать отказ
в обслуживании — приложение перестанет отвечать на обычные запросы.

**Почему приемлемо сейчас**: доступ ограничен локальной сетью, пользователь
один.

**Триггер для фикса**: обязательно до выхода за пределы локальной сети.
Варианты — `limit_req` в nginx на уровне прокси (проще всего, конфиг уже
есть), либо счётчик попыток в Redis с блокировкой по IP и по учётной записи.
Второй вариант точнее, но требует Redis, которого пока нет в стеке.

**Issue**: создать вручную

## 20. Нет подтверждения email и восстановления пароля

**Где**: `app/api/v1/endpoints/auth.py` — регистрация сразу выдаёт доступ,
забытый пароль восстановить нельзя.

**В чём проблема**: адрес не проверяется, поэтому можно зарегистрироваться на
чужой или несуществующий. Забыв пароль, пользователь теряет доступ навсегда —
сбросить его можно только вручную в базе.

Побочно: ответ 409 на существующий адрес позволяет перебором выяснить, кто
зарегистрирован (user enumeration). Скрыть это можно только подтверждением
по почте: отвечать 201 всегда, а письмо отправлять лишь новому адресу.

**Почему приемлемо сейчас**: одна учётная запись, которую создаёт владелец
сервера. Отправка почты требует внешнего сервиса (SMTP или API вроде
Resend), настройки SPF и DKIM — это отдельная инфраструктурная задача.

**Триггер для фикса**: появление пользователей, кроме владельца.

## 21. Задачи не привязаны к владельцу

**Где**: модель `Task` не имеет поля с идентификатором пользователя.

**В чём проблема**: любой аутентифицированный пользователь видит и меняет все
задачи. Для командного трекера это нормальное поведение (в Jira задачи проекта
видны всей команде), но нет и следа о том, кто что создал — то есть нет
аудита. При разборе «кто удалил задачу» ответа не будет.

**Почему приемлемо сейчас**: пользователь один, конфликтовать не с кем.

**Триггер для фикса**: появление второго пользователя. Минимальный шаг —
поле `created_by` для аудита (миграция с nullable, поскольку существующие
строки владельца не имеют). Полное разграничение доступа — отдельная задача:
понадобятся понятия проекта и роли, иначе привязка задачи к одному
пользователю превратит командный трекер в личный список дел.
