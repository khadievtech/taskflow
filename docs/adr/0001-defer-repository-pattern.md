# ADR-0001: Отложить Repository Pattern до появления второй сущности

## Статус
Принято — 2026-07-20

## Контекст
При проектировании структуры backend встал вопрос: вводить ли отдельный
слой `repositories/` между `services/` и `models/`, который бы инкапсулировал
все SQLAlchemy-запросы за интерфейсом (`get_by_id`, `list_all`, `create`, ...),
вместо того чтобы `services/task_service.py` обращался к `AsyncSession`
напрямую.

На момент решения в проекте одна сущность — `Task`.

## Рассмотренные варианты

**Вариант A — добавить `repositories/` сейчас**
- Плюсы: чёткая граница "SQL живёт только здесь"; сервисы становятся
  тривиально unit-тестируемыми с фейковым репозиторием вместо реальной БД;
  учебная ценность — паттерн часто спрашивают на собеседованиях Middle+.
- Минусы: для одной сущности это лишний уровень косвенности — 1 файл
  превращается в 2 (`task_repository.py` + `task_service.py`), большая часть
  методов репозитория была бы тонкими обёртками без собственной логики.

**Вариант B — отложить, пока `services/` обращается к сессии напрямую**
- Плюсы: меньше файлов и абстракций на старте; это то, как делают многие
  официальные примеры и small-team FastAPI-проекты; легко ввести
  Repository позже, когда появится реальный повод.
- Минусы: если бизнес-логика начнёт делать сложные повторяющиеся запросы
  в нескольких сервисах, придётся рефакторить в момент, когда это уже
  не так дёшево, как сделать сразу.

## Решение
Выбран **Вариант B**. Repository Pattern будет введён, когда наступит один
из триггеров:
- в проекте появится 2-я и 3-я связанные сущности (например, `Project`,
  `Comment`) с пересекающимися запросами;
- потребуется unit-тестировать `services/` без реальной БД (сейчас тесты
  идут через реальный Postgres на уровне HTTP-эндпоинтов, чего пока
  достаточно);
- один и тот же нетривиальный запрос начнёт повторяться в 2+ сервисах.

## Последствия
- `app/services/task_service.py` продолжает принимать `AsyncSession` и
  строить запросы через `select(...)` напрямую.
- Когда триггер наступит, миграция на Repository — это добавление нового
  слоя без изменения публичного API `services/`, а значит без изменения
  `endpoints/` — рефакторинг локализован.
