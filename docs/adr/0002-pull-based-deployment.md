# ADR-0002: Pull-based деплой через Watchtower вместо push по SSH

## Статус
Принято — 2026-07-28

## Контекст
После настройки публикации образов в GHCR (Phase 3a) нужно было решить, каким
образом целевой сервер получает новую версию приложения. Целевая площадка —
домашний сервер (старый ноутбук с Ubuntu) за обычным роутером провайдера,
без статического IP и без выделенной сетевой инфраструктуры.

## Рассмотренные варианты

**Вариант A — push: GitHub Actions заходит на сервер по SSH и обновляет стек**
- Плюсы: обновление мгновенно после мерджа; полный контроль над порядком
  шагов деплоя; легко добавить smoke-тесты после раскатки.
- Минусы: требует, чтобы GitHub мог инициировать соединение к домашней
  машине — то есть проброс порта на роутере, DDNS, приватный SSH-ключ как
  секрет в GitHub. Открытый наружу SSH на домашнем роутере — реальная
  поверхность атаки, несоразмерная ценности pet-проекта.

**Вариант B — pull: сервер сам периодически проверяет registry**
- Плюсы: наружу не открывается ни один порт — сервер инициирует только
  исходящие соединения; в GitHub не нужно хранить приватный ключ доступа
  к домашней машине; работает за любым NAT без настройки роутера.
- Минусы: задержка обновления (интервал поллинга); меньше контроля над
  процессом раскатки — нет места, куда вставить проверку после деплоя;
  сервисы обновляются независимо и могут разъехаться по версиям.

## Решение
Выбран **Вариант B**, реализация — Watchtower с интервалом 60 секунд,
`--label-enable` и `--cleanup`.

Детали реализации и их обоснование:
- Обновляются только контейнеры с лейблом `com.centurylinklabs.watchtower.enable`
  — то есть `backend` и `frontend`. Сервис `db` намеренно **не** помечен:
  автоматическое обновление мажорной версии Postgres без контроля человека
  может привести к несовместимости формата данных. БД обновляется вручную.
- `--cleanup` обязателен: без него старые слои образов накапливаются и
  со временем заполняют диск домашней машины.

## Выбор образа Watchtower
Изначально был взят `containrrr/watchtower` — де-факто стандарт на протяжении
лет. Оказалось, что репозиторий **архивирован 17.12.2025** (авторы публично
сообщили о потере интереса и времени), и образ несовместим с Docker 29+:
встроенный клиент работает по API 1.25, который современный демон отклоняет.

Перешли на `nickfedor/watchtower` (`nicholas-fedor/watchtower`) — наиболее
активно поддерживаемый форк, drop-in замена, автонегоциирует версию API.

Важная оговорка: авторы оригинала не одобрили официально ни один форк и
предупредили, что часть форков низкого качества. Это выбор сообщества, а не
официальная преемственность — при дальнейшей работе стоит периодически
проверять активность репозитория.

## Последствия
- Файл `docker-compose.prod.yml` описывает production-стек отдельно от
  `docker-compose.yml` (dev): образы берутся из GHCR, а не собираются локально,
  добавлены `restart: unless-stopped` и Watchtower.
- Сервисы обновляются независимо и в разное время (наблюдалось расхождение
  ~2.5 минуты между frontend и backend, т.к. arm64-сборка backend под QEMU
  идёт дольше). В этот промежуток новый frontend работает со старым backend —
  для текущего масштаба некритично, но требует обратной совместимости API,
  если появятся breaking changes.
- **Watchtower — осознанно временное решение.** Авторы форка сами не
  рекомендуют его для production и советуют Kubernetes с CI/CD. На Phase 7
  его роль перейдёт к Deployment'ам и управляемым стратегиям rolling update,
  а Watchtower будет удалён.
