# ADR-0003: Отложить метрики контейнеров (cAdvisor)

## Статус
Принято — 2026-07-28

## Контекст
После настройки метрик приложения (Phase 4a) и логов (Phase 4b) в стеке
наблюдения остался пробел: четвёртый золотой сигнал — saturation — покрыт
только по соединениям Postgres. Нет данных о потреблении CPU, памяти, сети и
диска по контейнерам. Соответственно нет метрик и по frontend: nginx не имеет
эндпоинта `/metrics`, а сам React исполняется в браузере пользователя.

Стандартное решение для метрик контейнеров — cAdvisor, либо отдельным
контейнером, либо через встроенный в Alloy компонент
`prometheus.exporter.cadvisor` (идеологически предпочтительнее, поскольку
Alloy уже развёрнут как единый агент для логов и метрик).

## Что выяснилось при проверке

**1. На Docker Desktop для Mac компонент не работает в принципе.**
Документация Alloy: `prometheus.exporter.cadvisor` работает только когда Alloy
запущен на Linux-хосте. Docker Desktop для Mac и Windows запускают контейнеры
в Linux-виртуалке, что исключает мониторинг хоста. На других ОС Alloy пишет
предупреждение в лог, и метрики не собираются.

Текущая площадка — MacBook (prod-стек развёрнут там как репетиция, отдельного
сервера пока нет), поэтому проверить работу компонента невозможно.

**2. На Linux встроенный cAdvisor сломан с Docker 29.**
Открытые issue в репозитории Alloy (#4864, #5021): Docker 29.0.0 сменил
драйвер хранилища с `overlay2` на `overlayfs`, а встроенный в Alloy форк
cAdvisor основан на версии 0.47.0 и обращается по старому пути. Ошибка:
`open /var/lib/docker/image/overlay2/layerdb/.../mount-id: no such file or
directory`. Подтверждено на Debian 12 и Ubuntu 24.04 с Docker v29+.

Установленная версия Docker — 29.6.1, то есть проблема затронет и будущий
Ubuntu-сервер, а не только текущую машину.

## Рассмотренные варианты

**Вариант A — добавить `prometheus.exporter.cadvisor` в Alloy**
Отклонён: не работает ни на текущей площадке (macOS), ни на целевой
(Linux + Docker 29) по двум независимым причинам выше.

**Вариант B — отдельный контейнер `gcr.io/cadvisor/cadvisor:v0.54.0+`**
Upstream-версия 0.54.0 поддерживает Docker 29, поэтому на Linux заработает.
Но на текущем Mac всё равно даст неполные данные или не запустится —
ограничение виртуалки Docker Desktop сохраняется. То есть компонент был бы
добавлен в репозиторий без возможности проверить его работу.

**Вариант C — отложить, зафиксировав причины**
Метрики контейнеров полезны, но не блокируют ничего из оставшегося плана.
Алерты (Phase 4c) дают больше пользы на том же объёме работы: сейчас никто
не узнает о проблеме, пока сам не откроет дашборд.

## Решение
Выбран **Вариант C**. Метрики контейнеров и наблюдаемость frontend
откладываются, причины зафиксированы здесь и в `docs/tech-debt.md`
(пункты 14–16).

Принцип, которым руководствовались: не добавлять в репозиторий компонент,
работоспособность которого невозможно проверить на доступной площадке.
Непроверенная конфигурация создаёт ложное чувство покрытия — хуже, чем явно
зафиксированный пробел.

## Условия для пересмотра
- Появился Linux-сервер (не Docker Desktop) — тогда осмысленен Вариант B с
  отдельным контейнером cAdvisor версии 0.54.0 или новее.
- Alloy обновил встроенный форк cAdvisor до версии, поддерживающей Docker 29
  (следить за issue #5021) — тогда предпочтителен Вариант A, поскольку не
  требует отдельного сервиса.
- Переход в Kubernetes (Phase 7) — там метрики контейнеров отдаёт kubelet
  через встроенный cAdvisor, и вопрос снимается сам собой. Это, вероятно,
  самый реалистичный путь закрытия пробела.
