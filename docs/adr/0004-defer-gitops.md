# ADR-0004: Отложить GitOps (ArgoCD/Flux), синхронизация вручную

## Статус
Принято -- 2026-08-26

## Контекст
За время работы над Phase 7-8 несколько раз проявилось расхождение между
состоянием манифестов в git и реальным состоянием кластера: PR с
обёрткой `opentelemetry-instrument` в `60-backend-deployment.yaml` был
смёржен в `main`, но под в кластере продолжал работать со старой командой
запуска, пока не был выполнен `kubectl apply` вручную. Аналогично --
увеличенный лимит памяти Grafana в `00-kube-prometheus-values.yaml`
сначала был применён напрямую через `helm upgrade`, и лишь позже, отдельным
коммитом, зафиксирован в git.

Это прямое проявление пункта 17 реестра техдолга ("конфигурации мониторинга
не доставляются на сервер автоматически"), зафиксированного ещё в Phase 4,
но теперь актуального для всего кластера, а не только для стека
наблюдения.

## Рассмотренные варианты

**Вариант A -- внедрить GitOps (ArgoCD или Flux)**
Контроллер внутри кластера сам следил бы за `infra/k8s/base/` и
`infra/k8s/observability/`, применяя изменения автоматически при каждом
мердже в `main`, и откатывая любые расхождения (drift), включая случайные
правки через `kubectl`/`helm upgrade` в обход git.
- Плюсы: устраняет самый источник сегодняшних расхождений; git становится
  единственным источником истины буквально, а не по соглашению; полезный
  практический опыт для собеседований.
- Минусы: требует настройки отдельного контроллера, разбора синхронизации
  секретов (которые сознательно не лежат в git -- см. `.gitignore` для
  `*-secret.yaml`), связки `Application`-манифестов ArgoCD поверх уже
  существующей структуры. Объём работы сравним с отдельной фазой, а не
  точечным улучшением.

**Вариант B -- продолжать синхронизировать вручную**
`kubectl apply -f infra/k8s/base/` и `helm upgrade` по-прежнему выполняются
человеком после каждого изменения.
- Плюсы: ничего не меняется прямо сейчас, ноль дополнительной сложности.
- Минусы: расхождение остаётся возможным при каждой забытой команде.

## Решение
Выбран **Вариант B**. За сегодняшний день расхождение случалось дважды,
и оба раза обнаруживалось и исправлялось за одну-две команды, без потери
данных и без сколько-нибудь заметного простоя. Цена ошибки на масштабе
"один разработчик, один домашний кластер" остаётся низкой -- забытая
команда стоит нескольких минут отладки, а не риска для продакшена с
реальными пользователями.

Полноценная настройка GitOps добавила бы объём работы, сравнимый по
масштабу с самой Phase 7/8, ради устранения проблемы, которая пока не
причиняет реального ущерба -- только неудобство, о котором легко забыть
и легко вспомнить.

## Последствия
- Пункт 17 реестра техдолга остаётся открытым и теперь явно ссылается на
  этот ADR как на причину, почему решение отложено, а не просто забыто.
- При каждом изменении `infra/k8s/base/` или `infra/k8s/observability/`
  необходимо не забывать применять его к реальному кластеру отдельной
  командой после мерджа -- ручная дисциплина, не автоматика.
- Дальнейшие правки в кластере, сделанные в обход git (как это было с
  лимитом памяти Grafana), нужно не забывать переносить обратно в
  манифесты -- источником постоянных расхождений сегодня были именно
  такие "быстрые правки на месте".

## Условия для пересмотра
- Появление второго разработчика или второго кластера (staging/prod) --
  тогда ручная синхронизация перестаёт масштабироваться.
- Реальный инцидент, вызванный именно расхождением git/кластера, а не
  предотвращённый вовремя замеченной проверкой.
- Отдельное желание освоить GitOps как учебную цель, не привязанную к
  конкретной боли -- законная причина, но тогда стоит выделить это как
  отдельный этап, а не встраивать походя в другую работу.
